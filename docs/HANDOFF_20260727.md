## 二、线上环境的真实形态（花了很多轮才问清楚，别再推一遍）

**是 Docker 服务，不是原生运行时。**仓库里的 `render.yaml` 描述的不是线上这个服务。

| 项 | 实际值 |
|---|---|
| 容器工作目录 | `/app`（镜像里代码在 `/app/src`） |
| **持久盘挂载点** | `/opt/render/project/src/buckets`（独立设备 `/dev/nvme25n1`，约 1G，用了 3%） |
| `/app/buckets` | **容器临时层**（`/dev/root`），不是盘 |
| `buckets_dir` 解析结果 | `/opt/render/project/src/buckets` ✅ |
| `OMBRE_BUCKETS_DIR` | `/opt/render/project/src/buckets`（面板设的，**优先级更高，是它救了数据**） |
| `OMBRE_VAULT_DIR` | 原为 `/app/buckets`（Dockerfile 烧死）；用户已在面板改齐 |
| `OMBRE_CONFIG_PATH` | `/opt/render/project/src/buckets/config.yaml` ✅ |
| 实际运行的代码 | **`<buckets_dir>/_app/src`**，不是 `/app/src` |

**`_app` 是设计不是 bug**：`entrypoint.sh:84` `CODE_DIR="$(dirname "$CONFIG")/_app"`，启动时把镜像代码复制到持久盘再从那儿跑，让 Dashboard 热更新能活过重启。重播种条件包含**镜像代码指纹**（`entrypoint.sh:125-128`），所以**不 bump VERSION 也能部署生效**。

### 关于路径的教训

不要从 `render.yaml` / `Dockerfile` 推断线上路径——那份蓝图和线上服务对不上。要事实就让用户在 Render Shell 跑：

```bash
cd /app && python -c "
import sys,os; sys.path.insert(0,'/app/src')
from utils import load_config
bd=os.path.abspath(load_config()['buckets_dir'])
print('buckets_dir =',bd); print('env =',os.environ.get('OMBRE_VAULT_DIR'),os.environ.get('OMBRE_BUCKETS_DIR'))"
df -h /app/buckets /opt/render/project/src/buckets
```

## 五、几个必须知道的代码事实

1. **`hold` 也依赖 LLM**。`tools/hold/core.py:44` 第一件事就是 `dehydrator.analyze()`，失败即 raise。所以任何「降级为 hold」的方案在 429 下都是无效的——§1.2 是绕开它直接落桶的。

2. **`bucket_mgr.create()` 在 embedding 失败时会删文件并抛**（`bucket_manager.py:493-501`）。这是写死的不变量（不允许「文件在但向量缺」）。§1.4 的待处理区是绕开这条约束**又不违反它**的做法——不要去破例改它，要改得单独跟用户确认。

3. **`create()` 会重写桶名**：前置自己的时间戳，再过 `sanitize_name`（只留 `\w`/空白/中日韩/连字符）。方括号、括号、斜杠全被吃掉。**要打标记就用 tag，不要用桶名。**

4. **`src/server.py` 全文是 CRLF**。用 Python 默认模式读写会把 1262 行整篇重写、掩盖真实改动。必须 `io.open(newline="")`。已有测试 `test_tool_description_keywords.py::test_server_py_keeps_crlf_line_endings` 钉住。

5. **GitHub Actions 在本仓库从未运行过**（全仓库 workflow run 数为 0，应是账号/仓库层面关闭）。PR 上没有 CI 门禁，合并前必须本地跑全套。

6. **没有 `gh` CLI**，GitHub 操作走 `mcp__github__*` 工具。

7. **`pulse` 输出非常大**（会 dump 所有桶摘要），慎用，会吃掉大量上下文。

## 六、diary / 待处理区的设计边界（别改坏）

**diary**（`src/tools/diary/core.py`）
- 独立 `<buckets_dir>/diary.db`，表 `diary(id, date, content, created_at)`，`date` 建索引
- `date` 是**记录归属的日期**不是写入时间；同一天多条、追加不覆盖
- `diary_read(days)` 收进 `[1,7]`，`date >= today-(days-1)` 且**不设上界**（提前写的未来日期不被吞）
- 判断标准写在工具 description 里：「这件事明天还在不在？」在→diary，不在→不记
- **不调 dehydrator、不建向量、不参与 breath/dream/decay** —— siliconflow 429 时必须可用，这是它存在的前提
- 明确不做：迁移旧数据、删除/编辑接口、7 天以上查询

**pending_store**（`src/pending_store.py`）
- 独立 `<buckets_dir>/pending.db`，表 `pending_writes`
- `record()` 任何情况下都不抛（坏路径返回 0）——调用方在救火
- **只有写入，没有对账**。对账补建要跟 §2.1 的 letter `PENDING_MIGRATE` 回迁**合并成同一个函数**，不许写两套
- 已有守卫测试：本模块出现 `migrate`/`reconcile`/`rebuild`/`flush`/`retry` 类函数即失败
- 将来的对账函数必须同时认两种来源：本表 `status='pending'`，以及标题带 `PENDING_MIGRATE` 的历史 letter（已知一条：`ea47fc1b4ee5`，对应 plan `a86df2e98081`）。判定用 `is_legacy_pending_title()`，**子串匹配不要写死全名**（历史标题过了 `sanitize_name`，线上实际显示为 `PENDING_MIGRATE20260723`）
